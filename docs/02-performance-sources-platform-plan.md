# 性能、新闻源扩展与插件化评估和开发计划

日期：2026-10-20。状态：计划基线；插件 P0–P4 已完成首轮实现，F0 验收核对已完成，F1 Node API 的缓存命中、冷缓存、部分命中和旧缓存场景均完成 1,000 样本测量，F2-A/F2-B 已完成服务端采集总并发、等待队列和上游 origin 调度边界。完整计划仍包含响应体限制、慢源隔离、Web、Electron 和真实新闻源质量测量。插件进度见 [插件平台进度记录](04-crawler-plugin-implementation-progress.md)，性能基准见 [性能基线实施记录](07-performance-baseline-progress.md)。

基线：已发布的 `v0.6.1`（`93dfe43`），以及 Node API 缓存状态实测提交 `47386c9`。排期、指标和接口草案均为建议，不代表已取得的性能结果或发布承诺。当前主线仍使用版本号 `0.6.1`，标签之后的改动尚未发布。

## 1. 评估结论

项目适合逐步发展为可扩展的新闻聚合平台。近期先开放新闻源接入能力，再按真实需求验证独立采集插件。

保留 React + Vite + Nitro 单仓结构。Web 和 Electron 继续共用页面、状态与 service；桌面从安装包加载界面，通过远程 API 获取数据。采集、插件执行和业务数据库放在服务端。新增兼容的源类型不应要求编写桌面专用功能。

执行顺序：**性能基线 → 采集与缓存优化 → 共用前端优化 → 新闻源开发工具 → 配置型新闻源 → 独立采集插件试点**。新闻源质量治理贯穿各阶段。

近期不安排语言重写、全面微服务拆分、默认引入 Redis/消息队列、插件市场或第三方远程 UI 代码。只有实测瓶颈或明确接入需求，才增加对应组件。[跨系统架构提案](../architecture.md) 保持候选方案状态。

## 2. 当前基础与限制

以下结论来自源码检查和仓库内的发布记录。本轮没有执行压测或全部源站在线采样。

| 范围 | 当前事实 | 对计划的影响 |
| --- | --- | --- |
| 多平台 | `0.6.0` 已生成六个平台桌面包、Web 包和双架构 Docker 镜像 | 复用现有发布流程；产物生成与真实安装验收分别记录 |
| 新闻源数量 | `shared/sources.json` 有 76 个条目，含 16 个重定向条目、6 个 `disable: "cf"` 条目 | 不等于 76 个独立且可用的新闻源；先建立质量清单 |
| 适配器注册 | `server/getters.ts` 在构建时收集源模块；`defineSource` 接受函数或函数映射 | 已有模块化基础；尚无运行时插件安装和卸载机制 |
| 源 ID 与元数据 | `SourceID` 来自生成的 `sources.json`；前端直接导入元数据 | 服务端动态新增源后，现有客户端不能自动完整识别；需先处理注册与兼容 |
| 数据模型 | 已有 `NewsItem` 标准化、URL 去重、异常条目过滤和数量上限 | 扩展应复用此入口，避免每个插件建立独立格式 |
| 请求与缓存 | 已有同进程同源请求合并、SQLite/可选 D1、旧缓存回退与健康诊断 | 优先优化现有路径，不先替换数据库 |
| 批量采集 | 缺失源通过 `Promise.allSettled` 并发，批量响应等待任务结束 | 需要统一并发预算、队列上限和慢源隔离 |
| 超时重试 | 共用抓取默认单次超时 10 秒、重试 3 次；适配器可覆盖 | 单次超时不是整个任务期限；应限制排队、重试和解析总耗时 |
| 共用前端 | 已有 TanStack Query 轮询、Feed 分批显示和共用 renderer 配置 | 从体积、重复请求、重渲染与长期内存测量入手 |
| 外部节点 | 已有 v1 API、节点清单、上游诊断、熔断和下游清单鉴权 | 可复用协议经验；尚无跨节点新闻条目聚合，不能视为插件平台已完成 |
| CI | 已有 PR/主分支桌面检查、tag 发布前校验及多平台构建依赖 | 后续增加预算回归和适配器检查；旧文档中的“没有 PR/发布检查”已过时 |

现有验收缺口继续保留：真实登录与同步、PWA 离线恢复、Windows 安装后任务栏，以及 macOS/Linux 真实窗口与升级。D3 记录中的认证服务 HTTP 520 属于部署异常证据，尚不能归因于本项目性能。具体范围见 [多平台实施记录](01-web-electron-plan.md)。

## 3. 扩展边界与术语

| 术语 | 责任与边界 |
| --- | --- |
| 核心宿主（Host） | Nitro 服务端。管理注册、调度、网络策略、缓存、标准化、健康与 API |
| 新闻源适配器（Source Adapter） | 将站点或频道数据转换为 `NewsItem[]`；不直接操作用户状态、认证和数据库 |
| 新闻源清单（Source Manifest） | 描述 ID、名称、分类、刷新建议、运行环境与维护信息；只声明数据，不执行代码 |
| 新闻源开发工具（Source SDK） | 共用接口、抓取上下文、解析工具、本地样例测试和清单校验；先做仓库内部模块 |
| 配置型新闻源 | 运维配置的 RSS 或受限 JSON 字段映射；不包含脚本、`eval` 或任意模板执行 |
| 独立采集插件（Collector Plugin） | 独立部署和升级的采集服务，通过受限 HTTP 协议输出标准条目；协议分离本身不提供资源或网络隔离 |
| 前端扩展（UI Extension） | 新阅读组件或交互入口；首轮只允许审核后随应用构建的内置组件 |

目标调用关系：

1. Web / Electron 通过共用 service 调用 API。
2. 核心宿主读取缓存，或通过统一调度调用内置适配器、配置型源、独立采集插件。
3. 核心宿主验证并标准化结果，更新缓存、健康状态，再返回条目和陈旧程度。
4. 客户端按元数据和能力通用渲染，不直接执行源站解析或插件代码。

## 4. 性能主线

### F1：建立可重复的基线

范围：现有健康记录、`server/utils/source-fetch.ts`、`server/database/cache.ts`、共用 service 和新增本地基准脚本。先复用现有诊断，不先建设独立监控系统。

固定提交、硬件、运行版本、数据量和网络条件。服务端首轮采用与当前 CI 一致的 Node 24、pnpm 10.30.3；兼容性变更另验。报告记录 CPU、内存、启动方式、缓存状态、预热次数和样本数。

| 场景 | 测量方法 | 记录指标 |
| --- | --- | --- |
| 单源 / 批量 API | 单源、10 源、30 源；全命中、部分缺失、全缺失、旧缓存；预热后每档至少 1,000 个请求 | p50/p95/p99、吞吐、错误率、响应大小、缓存命中率、CPU/RSS |
| 并发与慢源 | 本地可控 HTTP 测试服务；1/10/30 客户端并发，注入慢响应、429、5xx、畸形响应 | 实际上游请求数、在途数、队列长度、排队/采集/解析耗时、取消后剩余任务 |
| 真实源质量 | RSS/JSON/HTML 各选代表源，低频在线采样，与本地压测分开 | 成功率、空列表原因、最后成功时间、发布时间完整率、重复率 |
| Web | 首页、Feed、源详情、洞察；固定桌面和移动设备配置，冷/热缓存各至少 5 次 | 压缩 JS、请求瀑布、LCP、交互耗时、CLS、长任务 |
| Electron | Windows 实际打包程序；冷/热启动各至少 5 次，30 分钟阅读/切页/最小化恢复 | 到首个可读内容耗时、主/渲染进程内存、CPU、网络请求数；有设备后补其他系统 |

使用保存的响应样例或本地测试服务测核心性能，避免混入源站网络波动。采集耗时和文章新鲜度分别统计；热榜没有发布时间时记录未知，不能用抓取时间替代。

以下为初始建议预算，F1 结束时根据实测冻结；调整需保留原因：

| 指标 | 建议目标与条件 |
| --- | --- |
| 缓存命中 API | 单实例、本地 SQLite、30 源且每源不超过 30 条、30 并发时 p95 ≤ 300 ms，错误率 < 1%；不含公网传输和冷采集 |
| 慢源隔离 | 默认 API 等待预算候选 8 秒；到期返回已完成/旧缓存及明确缺失原因，不因一个慢源丢弃其他源 |
| 首屏资源 | 压缩 JS 若超过 300 KiB，先争取下降至少 20%；固定 gzip/Brotli 口径，达标后维持预算 |
| 页面体验 | 以 LCP ≤ 2.5 s、INP ≤ 200 ms、CLS ≤ 0.1 为方向；真实访问量足够时按移动/桌面 p75 判断，实验室交互数据不能代替真实 INP |
| 桌面回归 | 同设备、同数据和网络下，启动耗时及稳定内存相对 F1 回退不超过 10%；反复切页后内存不能持续无界增长 |

页面阈值依据 [Web Vitals 官方说明](https://web.dev/articles/vitals)。以上是待测预算，不是当前线上指标。不能通过延长缓存却隐瞒陈旧程度来达标。

### F2：控制采集成本与缓存等待

范围：`server/utils/fetch.ts`、`source-fetch.ts`、`resolve-entire-sources.ts`、`resolve-source-response.ts`、缓存层和相关 API。

1. 建立统一采集调度入口，限制总并发、每目标主机并发、队列容量、任务期限和响应体大小。Node 候选起点：总并发 8、每主机 2、等待队列 100；F1 压测后校准。Edge 使用独立预算；RSSHub 等共享域名按真实请求目标计限额。
2. 排队、连接、重试、读取和解析共用任务期限。使用有上限的退避与抖动，遵守 `Retry-After`，期限不足不再重试。同步解析不能只靠超时中断，必须限制输入及计算量。
3. 保留同源请求合并。单个调用方取消只退出自身等待；没有其他等待者且不是后台刷新时，才取消共享采集。处理队列满、关闭、超时与资源释放。
4. 批量等待到期后保留部分结果、错误和旧缓存。新状态先验证旧客户端兼容，必要时新增响应版本。保留 Feed 分批显示；首轮不要求 SSE/WebSocket。
5. 区分新鲜缓存、可用旧缓存和无缓存。单次缓存写入失败不应丢弃已验证的新条目；必须报告存储异常，不能声称持久化成功。
6. 测量 JSON 编解码、查询和写入后，再决定是否增加有容量/TTL 限制的进程内 L1。公共 API 可评估条件请求；含用户状态或不同权限的数据分离缓存键及 HTTP 缓存策略。
7. Node/Docker 可选预热活跃源，按更新周期和访问热度安排任务；可靠调度需要可恢复的状态。Edge 不依赖响应结束后的长期任务，其生命周期受 [Workers 限制](https://developers.cloudflare.com/workers/platform/limits/) 约束。多副本全局去重与调度仅在实际需要时单独设计。

验收：慢源、故障源和饱和场景中，健康源按预算返回；上游请求数符合限制；队列、缓存与响应体有界；旧接口兼容测试通过。API 等待结束后任务是否继续，必须由调度模式明确决定。

回退：每项策略可单独关闭；关闭预热/L1/新调度后恢复旧路径，不改变已有源 ID 和缓存格式。

### F3：优化共用前端与桌面表现

范围：`vite.renderer.ts`、路由、`src/hooks/useNewsSource.ts`、`shared/source-query-schedule.ts`、service 与离线快照。

- 按 F1 结果拆分洞察、健康等非首屏路由及重依赖。当前自动拆分有历史兼容注释，先验证路由生成、PWA 和 Electron，再选兼容方案。
- 审计 Query 默认焦点行为、源刷新周期、手动刷新和 `cacheSources`。隐藏页面/窗口减少轮询，恢复时合并刷新并提示陈旧状态；停止请求不能冒充数据仍按时更新。
- 测量 Feed 排序、去重、热榜对比和重渲染，先消除重复计算与无必要动画。只有数据规模证明收益后才引入虚拟列表，并验证滚动定位和键盘操作。
- 为查询缓存、阅读历史、离线快照和图片定义容量与清理规则；数据格式升级保留迁移或兼容读取。
- Electron 仅补生命周期与资源统计；业务优化写在共用前端。每个切片验收 Web 和真实桌面窗口的切页、刷新、最小化恢复及断网提示。

验收：按 F1 同条件比较体积、首屏、交互、后台请求和桌面资源，至少修复一个已定位瓶颈并达到冻结预算。

回退：按路由或轮询策略独立撤回，不新增桌面专用业务页面。

## 5. 新闻源扩展主线

### F4：形成可维护的 Source SDK

范围：`shared/pre-sources.ts`、`shared/types.ts`、`scripts/source.ts`、`server/getters.ts`、`server/utils/source.ts`、适配器及贡献说明。

先迁移 RSS、JSON、HTML 各一个代表适配器。保留 `defineSource` 兼容包装，确认接口后分批迁移。

| 工作 | 具体要求 |
| --- | --- |
| 清单校验 | 拒绝重复 ID、重定向循环、缺少实现、非法平台声明和静默注册覆盖；生成失败退出非零 |
| 元数据 | 补维护者、原站链接、采集类型、分类、刷新建议、环境限制和维护状态；公开字段保持兼容 |
| 抓取上下文 | 宿主提供受限 fetch、取消信号、期限、脱敏日志和配置读取；禁止无限重试；可信内置代码仍需检查是否绕过入口 |
| 解析工具 | 复用 RSS/JSON/HTML、时间和 URL 标准化；限制响应大小、字段长度、条目数、分页与重定向次数 |
| RSSHub | 服务端地址可配置，记录依赖及降级行为，保留原默认值的回退路径 |
| 错误分类 | 区分无新内容、解析结构变化、限流、网络失败和停用；解析失败不能静默转成正常空列表 |
| 开发工具 | 模板创建、单源样例执行、清单校验、诊断报告；先做内部工具，不立即发布 npm 包 |
| 测试样例 | 正常、缺字段、空响应、重复、超大输入；保存前移除凭据和个人数据 |

验收：三类代表源通过相同检查；既有 ID、URL、排序语义和缓存兼容；新增内置源只需清单、适配器、样例和测试，不修改路由或 Electron。贡献教程能让另一名维护者独立接入。

回退：逐源恢复原适配器，旧 `defineSource` 继续可用；内部 SDK 稳定前不承诺长期公开 API。

### F5：质量治理、优先来源与配置型接入

先选 10 个已有重点源，覆盖综合、科技、财经、国际及三种采集方式；启动时按可访问性和需求冻结名单。新增源按每批 3–5 个推进，优先填补内容覆盖缺口。

| 优先级 | 来源类型 | 接入条件 |
| --- | --- | --- |
| 高 | 发布方 RSS/Atom、公开结构化 API | 更新持续、内容互补、URL/时间可规范化、调用条件可确认 |
| 中 | 稳定公开 HTML、受控 RSSHub | 有结构样例、维护者、故障识别方法与外部依赖记录 |
| 条件投入 | 浏览器渲染、专用会话和复杂采集 | 先证明内容价值及可持续维护；放在独立采集服务，不进入桌面进程 |

质量报告记录时段、次数、成功率、有效条目率、重复率、发布时间完整率、新鲜度和维护成本。重点源建议观察 7 天，最低样本数随更新频率确定；候选标准为成功率 ≥ 95%、有效条目率 ≥ 99%。未达标时标实验或停用；样本不足时不能写达标。低频源当天无新文章不等于故障。

配置型接入先支持 RSS 和受限 JSON 映射，由运维在服务端配置，不开放匿名用户提交任意 URL。前置工作：

1. 保留内置 ID 的类型检查，引入运行时验证的动态 ID 和源描述；不能简单将所有 ID 改成任意 `string`。
2. 设计外部命名空间，候选 `ext.<provider>.<source>`；验证长度、字符集、URL 编码、唯一性、缓存键与重定向。已有 ID 和别名保持不变。
3. 客户端通过版本化来源发现 API 合并动态描述。覆盖添加源、搜索/拼音、分类、Feed、源详情、健康、布局同步、收藏、历史与离线。停用/删除源时保留已保存文章。
4. 提供清单版本和能力声明。旧客户端无法识别时跳过并提示，不删除同步数据。先升级通用客户端，后续兼容的新源才可只更新服务端。
5. 网络策略限制目标、重定向和响应体；Node 检查私网/回环并固定 DNS 解析结果。Edge 无法满足同等约束时拒绝任意地址接入，改用明确允许的采集服务。

验收：一个 RSS 和一个 JSON 源可仅通过配置启停；已升级的 Web/Electron 无需为它们加代码或重新打包；旧客户端、同步及保存文章兼容测试通过。

回退：关闭动态清单，恢复内置列表；保留配置备份和动态来源历史数据。

## 6. 插件化方案与可行性

| 方案 | 可行性与成本 | 核心/客户端更新要求 | 建议 |
| --- | --- | --- | --- |
| 构建时内置源模块 | 最贴近现有结构，成本低，源更新跟随服务端发布 | 重建服务端；纯采集修复通常不影响桌面 | F4 首先完成 |
| RSS/JSON 配置型源 | 接入简单，需动态注册、网络限制及通用客户端 | 完成 F5 后兼容配置变更无需重建 | 首个对运维开放的扩展能力 |
| 独立采集服务插件 | 可独立发布及选择语言，适合浏览器采集；增加部署和鉴权成本 | 协议兼容时无需重建核心或客户端 | F6 条件试点 |
| 同进程动态 npm/JS | 与宿主共享权限和故障影响，Edge 兼容有限 | 仍需版本与卸载管理 | 近期不提供第三方动态加载 |
| 第三方 UI 与插件市场 | 需扩展点、代码隔离、兼容、分发和治理 | 无法承诺任意 UI 自动跨端兼容 | 有真实需求后单独评估 |

`node:vm` 不能作为运行不可信代码的安全机制，参见 [Node.js 官方说明](https://nodejs.org/api/vm.html)。独立进程或 Worker 也不能单独代替权限、网络和资源限制。试点采用受控容器/服务、非特权用户、最少挂载、出站限制及 CPU/内存上限。

Electron 保留本地页面、关闭 Node 集成、上下文隔离和受限 IPC。插件不获得主进程或 preload 能力。此边界遵循 [Electron 安全建议](https://www.electronjs.org/docs/latest/tutorial/security)，也保持 Web 功能直接复用到桌面的开发方式。

### F6：独立采集插件试点（条件阶段）

2026-10-27 排期调整：先启动 F6-A“协议与宿主边界收口”。F6-A 固化清单资源预算、共享网络权限检查和跨宿主离线验收；F6 的独立插件试点仍需真实外部需求或两个独立发布适配器作为进入条件。详见[插件化架构排期](24-crawler-plugin-architecture-roadmap.md)。

启动条件：F2 预算、F4 SDK、F5 动态注册已验收；出现至少两个需要独立发布的真实适配器，或外部维护者明确接入。条件不满足时继续模块化单仓，不建设完整平台。

先做一个参考插件和一个不同采集方式的插件。复用 v1 条目格式、节点清单及超时/熔断经验，但另行定义采集协议；现有节点清单鉴权不能直接视为新闻条目读取授权。

| 协议范围 | 最小要求 |
| --- | --- |
| 身份和兼容 | 插件 ID、插件版本、协议版本、宿主兼容范围、源命名空间；版本分别处理，明确拒绝不兼容项 |
| 输出能力 | 源清单、读取条目、健康状态；运行时验证必需字段，忽略未知可选字段；宿主限制数量和响应大小 |
| 配置和凭据 | 配置 schema、服务端秘密引用、专用 scope；不得复用用户 Cookie、GitHub token、SyncHub key 或节点清单 key |
| 执行和失败 | 总期限、取消、重试上限、限流、熔断、缓存和陈旧标记；异常插件不阻塞内置源 |
| 权限执行 | 清单声明能力/目标主机，部署层强制网络、文件和资源限制；声明不等于隔离 |
| 生命周期 | 登记 → 校验 → 试探 → 启用 → 暂停/升级 → 回退/移除；记录版本、操作者、结果及脱敏诊断 |

核心宿主拥有缓存、标准化和客户端 API；插件不写主库或用户状态。元数据、文章和图像 URL 作为不可信输入校验。运维管理需独立授权，读者界面只显示必要的健康与陈旧提示。

验收：独立升级、不兼容版本、429、超时、超大/错误响应、进程退出、凭据轮换和回退均通过；故障时内置源可读，宿主延迟及内存符合预算；记录接入、升级和维护成本。

继续平台化的条件：外部维护者能按文档独立接入两个插件；升级不修改核心；隔离与兼容测试通过；运维成本可接受。否则保留 SDK 与配置型源，停止扩张管理功能。

后续扩展顺序为“采集 → 受控内容处理/导出 → UI”。去重和排序先留核心，出现明确策略差异后再开放接口。插件市场、用户上传代码、收费分发和远程 UI 执行不在本计划实施范围。

## 8. 验证与回退规则

- 纯文档：UTF-8、LF、链接、Markdown 结构、`git diff --check`；应用测试与 UI 验收不适用。
- 共享接口、采集、缓存和源模块：`pnpm lint:check`、`pnpm typecheck`、`pnpm test --run`，补对应调度/兼容/解析测试；阶段结束执行 `pnpm build`。
- 影响桌面共用代码：追加 `pnpm typecheck:electron`、`pnpm test:electron`、`pnpm electron:build`。UI 使用 Computer Use 和真实窗口；无对应设备时明确缺口。
- 性能和 SDK 命令在 F1/F4 实现后再加入文档与 CI，本文不假定它们已存在。CI 用固定本地数据做预算回归；实源采样独立执行，避免源站波动阻塞全部 PR。
- 外部服务集成只使用本地 Docker，记录镜像/版本、端口、启动和清理结果。F6 实际运行插件并验证资源/网络限制；桩响应不能证明隔离和集成通过。Docker 不可用时标未完成。
- 比较同流量口径的错误率、p95、命中率、新鲜度和上游请求量。策略逐项可关，源/插件可独立停用。ID 或持久化格式迁移需独立备份与回退，不和并发调参混合发布。
- 发布继续生成桌面、Web 和 Docker 产物，说明来自标签提交范围；性能达标不替代登录、同步、离线和升级验收。
