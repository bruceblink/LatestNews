# N4-N：FTS 容量恢复对照

2026-11-25；父提交 036673b；同一隔离 Linux x64 / AMD EPYC 8 逻辑核 / Node 22.23.4 / SQLite（better-sqlite3 13.0.3）。测试使用 performance:article-capacity 生成确定性 fixture，未接触真实历史数据。先运行候选、后运行父提交、再运行候选；非随机化三轮正式 API 性能试验。

## 修改与一致性

旧重建按 key 每页 UNION 扫描 FTS 虚表，再按未索引的 article_key 删除/插入；10 万篇规模下反复扫描成本过高。

新版保持 article_fts_repair 表和 phase 状态契约，generation 增加 fts-v2 前缀，cursor 表达清理、主键重建及校验进度：
- 清理阶段每个原子批次最多删除 200 个派生 FTS rowid，不扫描或删除源文章、来源、事件、缓存或 journal。
- 重建阶段每批 50 个有序 article_key，读取实际文章；只插入一次，更新游标和该批 pending 原子完成。generation/cursor 守卫避免并发覆盖进度。
- 所有新文章写入仍持久标记 pending。repairing 时暂停常规 FTS 更新，查询保留字面回退；验证阶段逐批处理游标后方的新增和更新。
- 只有 pending 为空且事务内全量一致性检查通过才发布 ready。验证失败则开启新 generation；持续写入或故障可能使修复继续 pending，不承诺固定时间。旧算法未完成的游标按新 generation 从清理开始。
- 派生索引可能暂时为空，但不会以 FTS 模式对外展示半成品；历史文章和事件不删除。无新 schema 或依赖。旧版本不理解新游标，回退前必须完成修复并确认 ready/一致，或在隔离备份上恢复；禁止新旧写入器混跑。
