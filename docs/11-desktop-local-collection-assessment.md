# 桌面本地采集可行性与实施建议

日期：2026-10-24。评估范围：远端新闻 API 未配置或不可用时，Electron 在本机获取新闻。本次只评估，不改变桌面运行策略。

## 结论与术语

可行，建议优先扩展现有 Electron 采集子进程。应用界面继续从安装包加载，通过进程间通信（Inter-Process Communication / IPC）请求本地数据。第一阶段不需要监听 HTTP 端口，也不要求用户另装 Node.js。

- 桌面采集协调器：由主进程持有配置、任务调度、缓存和状态；不执行站点解析。
- 采集子进程：使用 Electron `utilityProcess` 执行已审核的适配器，完成、失败或取消后回收。
- 本地 HTTP 服务：仅在需要让浏览器或其他本机客户端共享 API 时增加，不能与桌面采集子进程混为一谈。
- 托盘后台模式：窗口关闭后应用仍运行并按计划刷新；不同于应用退出后仍存活的独立系统服务。

远端服务故障与本机断网分别处理。远端故障时，本机仍需能够访问新闻源站；本机断网时，只能读取已有缓存。

## 当前源码证据

| 能力 | 当前实现 | 缺口 |
| --- | --- | --- |
| 子进程 | `electron/crawler-host.ts` 使用 `utilityProcess.fork`，复用 `ProcessCrawlerHost` | 当前按采集任务启动，未提供持续后台刷新 |
| 调度 | `electron/crawler-plugin-provider.ts` 限制并发 2、排队 24、排队与执行各 15 秒 | 还需同源合并、持久缓存及目标站限频 |
| 本地目录 | 从 `<userData>/crawler-plugins/enabled.json` 读取启用包，核对包摘要和来源清单 | 安装包只携带 worker 入口，尚未预置全部适配器包 |
| 客户端路由 | `src/services/source.service.ts` 对已支持来源优先请求远端；网络失败或 5xx 时回退本地插件 | 首个回退切片已实现；本地持久缓存已写入 Electron `userData` |
| 来源覆盖 | 本地可信目录包含 Pcbeta、Freebuf、掘金、Hacker News 四个包 | 不等于全部内置来源支持本地采集 |
| 来源发现 | `src/main.tsx` 尝试合并远端与本地来源描述 | 来源详情和健康 service 仍直接请求远端，不能仅靠条目回退完成页面 |
| 配置 | 可保存远端 origin；空地址表示仅本地模式 | 已实现；尚无独立 remote/auto/local 枚举和后台刷新设置 |
| 缓存 | Electron 主进程把本地采集结果保存到 `crawler-cache.json`；采集异常时返回降级或旧缓存 | 文件上限 2 MiB、64 个来源、每源 100 条；细节见[持久缓存方案](14-desktop-persistent-crawler-cache.md) |
| 退出 | `electron/main.ts` 退出前调用 provider `dispose()`；非 macOS 最后窗口关闭后退出 | 尚无托盘后台开关、后台状态和自启动管理 |

## 两种方案比较

| 方案 | 优点 | 代价与适用条件 |
| --- | --- | --- |
| 主进程协调器 + IPC + 采集子进程 | 复用已有宿主，不占端口，适合桌面应用；解析不阻塞主线程 | 需补齐本地 service、缓存、来源目录、健康与模式切换；首选 |
| 完整本地 Nitro HTTP 服务 | 便于复用整个现有服务端 API，也可让本机浏览器连接 | 需额外打包服务端及数据库依赖，管理端口、启动检查、访问认证、升级和退出；有共享 API 需求再做 |
| 应用退出后独立常驻服务 | 桌面关闭后仍能采集，可服务多个客户端 | 增加服务安装、自启动、跨平台升级、版本协调与卸载清理；单独阶段 |

首选方案中的协调器随应用存活，解析 worker 按任务运行或使用有上限的进程池。只有观测到进程启动成本明显影响体验时，才改为长期 worker；不让故障 worker 无限存活。

## 建议的数据路径与切换规则

调用方向为：共用页面 → 新闻 service → 桌面协调器 → 远端新闻 API 或本地采集子进程 → 统一结果与缓存。认证和 SyncHub 保持独立的网络与凭据边界。

| 模式 | 读取路径 |
| --- | --- |
| `remote` | 使用配置的远端，明确显示失败；不自动触发本地抓取 |
| `local` | 直接读取本地缓存，按来源间隔刷新已支持来源；不等待远端 |
| `auto` | 远端可用时使用远端；未配置远端时直接本地；网络失败、超时或可重试服务端故障时回退本地 |

- 为整批远端请求设置有限等待预算，建议从 2 秒开始测量；不能逐源串行等待完整超时后才启动本地任务。
- 连续服务端失败后短期暂停远端请求，再以退避和少量探测恢复。429 遵守 `Retry-After`，不以本地抓取绕过源站限频。
- 401/403 表示权限问题，不静默改走本地。合法空列表属于正常结果。只有 API 路径被明确判定不兼容时，才把 404 作为服务能力缺失处理。
- 本地不支持的来源保留已有缓存并说明原因；一个来源失败不能清空其他来源。不能承诺任意内置来源自动转成本地插件。
- 报告实际数据来源、更新时间、缓存状态、失败原因及下一次允许重试时间。切换模式后清理对应查询状态，避免把远端与本地数据的时效混在一起。
- 收藏、阅读历史和离线文章不随来源停用或模式切换而删除。

## 资源、持久化与安全边界

- 初期沿用并发 2、队列 24、执行 15 秒和解压后响应 2 MiB 上限。增加每站限频、共享采集、取消传播和总等待期限；参数按桌面实测再调整。
- 本地缓存位于 `userData`，由协调器单独负责写入。首批按已支持来源保存有限条目，限制文件大小、来源数和历史容量；写入使用原子替换，格式带版本。SQLite 可在多记录查询确有需要后引入，并先验证 Electron 原生模块打包。
- 主进程只提供固定的来源 ID 与操作 IPC，校验调用窗口和参数；渲染器不能传入脚本、文件路径或任意 URL。采集 worker 不获得登录 Cookie、JWT、SyncHub key 或主进程 API。
- 插件子进程和包摘要校验不构成不可信代码沙箱。首阶段只预置已审核包；网络权限、重定向和输出限制继续由宿主执行。
- 窗口隐藏、系统休眠和网络恢复需要明确刷新策略。恢复时合并过期任务，避免补跑每个错过的周期。
- 默认退出时取消队列、HTTP 和 worker，完成或终止待写缓存；托盘后台和开机自启动分别由明确设置启用。
- 如果后续增加 HTTP 服务，只监听回环地址并使用随机端口、会话级访问凭据和精确来源校验。不得绑定所有网卡或把登录凭据转给来源站点。

## 分阶段实施与验收

1. 本地数据能力：预置并验证首批可信适配器，补齐目录、详情、批量与健康读取。持久缓存已有容量限制和失败回退，仍需在真实桌面验收中验证断网与重启恢复。
2. 模式切换：增加 `remote/local/auto` 配置，支持远端地址为空，验证拒绝连接、超时、5xx、429、401/403、远端恢复和部分来源不受影响。外部服务模拟与依赖集成使用本地 Docker，公网观察另记。
3. 桌面验收：打包后禁用远端 API，Windows 真实窗口验证启动、来源列表、Feed、来源详情、刷新、最小化恢复和退出无残留任务。单独记录 CPU、内存和本地数据恢复，不以构建或 headless 替代真实窗口。
4. 可选后台：增加托盘开关、后台刷新、休眠恢复与资源预算，再验收升级和卸载。不在第一阶段安装系统服务。
